# Interview guide

This implementation and its repairs were developed with AI assistance in Codex. Explain the code you have inspected and tested; do not describe an invented independent manual coding history.

## 60-second overview

“DocVerify compares purchase orders, quotations, and invoices inside private cases. It extracts supported fields from selectable-text PDFs, preserves source pages, and lets a person review the values. Deterministic Decimal rules check arithmetic and differences. Stable row identities prevent repeated items from colliding; revisions stop stale tabs overwriting reviews. Reprocessing records new raw runs while keeping retained history and corrections on their own extraction basis. Search distinguishes original PDF passages from current reviewed records. Keyword rules and a trained synthetic TF-IDF classifier handle type prediction; optional pretrained embeddings rank passages, and an optional Claude API generates cited answers. I evaluated the runtime chunk pipeline separately from the earlier whole-document baseline. All quality data is synthetic, and I do not claim production readiness or general extraction accuracy.”

## Five-minute demo

1. **0:00–0:45:** Register or sign in. Load sample cases explicitly. Explain user → case → document ownership and the difference between source files and database metadata.
2. **0:45–1:30:** Open the quantity/price sample. Show the selected purchase-order reference and invoice target, INR 2,200 subtotal delta, the rule label, and page links. Explain why code uses Decimal instead of asking a model to multiply.
3. **1:30–2:20:** Open the invoice, change quantity/price/amount/subtotal/total to the matching values, and save. Show refreshed findings, the immutable first retained extraction, and the before/after audit.
4. **2:20–3:10:** Add two identical Washer rows or show the regression test. Explain distinct persistent row IDs and stable finding identities. Show the row-reordering regression: acknowledgements remain attached. A changed quantity reopens its finding.
5. **3:10–3:50:** Show a mixed readable/unreadable PDF in the test or a fictional example. A normal field save keeps the OCR limitation; a reasoned manual source review is a separate audited action. Do not claim OCR exists.
6. **3:50–4:25:** Search original source, then current reviewed data. Without a key, show honest evidence-only mode. Explain that corrected supplier values are reviewed records, not original quotations.
7. **4:25–5:00:** Export JSON/CSV and open actual metric files. Runtime retrieval Recall@5 is 0.800 and MRR 0.600 on the current synthetic test; the harder classification challenge macro-F1 is 0.667. Explain validity limits and the next improvement you would measure.

## Twenty questions grounded in the code

1. **What is frontend versus backend?** Next/React renders forms and PDF review (`frontend/components`). FastAPI authorizes requests, validates inputs, and runs services (`backend/app/api`). A hidden frontend button is not an access check.
2. **What is an API request here?** `lib/api.ts:api` sends JSON or multipart data to same-origin `/api`; `next.config.ts` forwards it internally. For example, upload creates metadata and a job, not an immediate completed extraction.
3. **How do accounts work?** `api/accounts.py` and `auth.py` hash passwords with Argon2, store only hashes of random session tokens, use an HttpOnly cookie, and validate session expiry. The CSRF header plus Origin check protect mutations. Throttling is in-process, not distributed.
4. **What database relationships matter?** `models.py`: users own cases; cases contain documents/findings; documents have jobs, pages, chunks, runs, and corrections. PDFs are on a persistent local volume. Cascades remove derived rows only when the owning case/document is intentionally deleted.
5. **Why a background job?** `worker.py` separates slow PDF/model work from the upload request. The database already provides durable storage, so a modest single-worker queue avoids adding Redis/Celery without demonstrated need.
6. **What prevents two claims or late writes?** Conditional job update and PostgreSQL row locks; a lease token must still match at completion. A stale processor cannot replace a newer run. There are bounded retries and stale-lease recovery, but no heartbeat/throughput production claim.
7. **What extracts fields?** `extraction.py` uses pdfplumber and rule-based labelled metadata/three line layouts. This is not a learned extraction model. Unknown/conflicting values remain null. Image-only PDFs fail explicitly; mixed-page limitations remain reviewable.
8. **Why Decimal?** `verification.py:dec` constructs Decimal from strings. Binary floats can represent money inexactly. Tolerance is explicit; zero is an actual value and null means unknown. Tax-rate checking needs an explicit rate.
9. **Why separate uncertainty from differences?** An unreadable quantity does not establish a mismatch. Structural warnings survive field saves (`review_state.py`); supported numeric differences and within-document arithmetic checks have their own finding types.
10. **How do items match?** `matching.py` prioritizes compatible identifiers, then exact normalized descriptions, then fuzzy candidates. Conflicting IDs and duplicate/competing matches require review. A fuzzy threshold is not an identity guarantee and does not produce confirmed numeric deltas alone.
11. **How was the duplicate finding bug fixed?** Each row has a persistent ID. Finding identity includes the rule, reference/target, relevant row IDs and material facts. Two identical Washer rows stay distinct; no IntegrityError workaround or random result-ID refresh is used.
12. **What happens on reordering or changed values?** Reordering existing row IDs keeps unchanged findings and review status. Changed expected/observed facts change the material hash and reopen the result. Deleting/re-adding creates a new row. Tests define these policies.
13. **How do stale tabs behave?** `corrections.py:check_revision` conditionally increments the expected document revision. A mismatch returns 409; the editor preserves its draft and offers reload/discard. The guarded hook also cancels or ignores a slower request for another document.
14. **Is original really immutable?** New documents retain their first successful extraction, and every run is recorded. Old data can only retain the snapshot that existed at migration; earlier overwritten history cannot be recovered. Legacy timestamps/correction bases are labelled unknown. Corrections stay bound to their own run.
15. **What comparison workflow is supported?** `comparison_scope` picks one unambiguous purchase order automatically or uses explicit selection. It compares that reference with individual targets, never target pairs. Multiple invoices warn about partial fulfilment; aggregation is unsupported. Readiness reports failed/unreadable/incomplete data even with zero findings.
16. **Which part is trained ML?** `scripts/train_classifier.py` fits TF-IDF plus logistic regression on synthetic text. Keyword type rules are a separate baseline. The model artifact hash and configuration are recorded with runs. The classifier does not calculate invoice discrepancies.
17. **Which part uses pretrained models or an external API?** Sentence Transformers optionally loads MiniLM embeddings to rank passages. Claude Messages is an optional external answer API. The app works without either. No live semantic/provider quality result is claimed.
18. **Retrieval versus generation, and whose values are answered?** Retrieval finds original page chunks. Generation writes a response from explicit original or reviewed scope. Reviewed scope includes complete effective records and audit/run revisions, separately labelled from PDF text. Citation membership is validated, but sentence-level entailment is not independently proven.
19. **How is evaluation honest?** Old whole-PDF metrics remain labelled a synthetic document-level baseline. New evaluation uses runtime chunking/ranking within cases, validation-only threshold selection, and held-out test cases. It includes paraphrases, ambiguous and unsupported questions. The classifier challenge exposes the missing unknown-class detector. Synthetic repeated phrases still limit credibility.
20. **What would you improve, and what cannot you claim?** Collect consented, independently labelled unseen-vendor data; improve extraction/source alignment and answer-support evaluation; then add worker heartbeats, optimistic merge/rebase tools, backups/restore automation, processing isolation and deployment hardening. This version cannot claim general supplier parsing, OCR, invoice aggregation, calibrated uncertainty, LLM factuality guarantees, or production readiness.
